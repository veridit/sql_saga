Subject: pg_dump omits FK dependencies between extension config TABLE DATA entries; parallel pg_restore fails

PostgreSQL version: 18.3 (reproduced); the same code is in REL_18_STABLE (18.7) and master as of 2026-11-13
Operating system: macOS 14 (aarch64), Postgres.app build

PostgreSQL 18.3 (Postgres.app) on aarch64-apple-darwin23.6.0, compiled by Apple clang version 15.0.0 (clang-1500.3.9.4), 64-bit
pg_dump (PostgreSQL) 18.3 (Postgres.app)
pg_restore (PostgreSQL) 18.3 (Postgres.app)

Description

When an extension has two configuration tables (registered with pg_extension_config_dump) and one references the
other with a foreign key created by CREATE EXTENSION, a custom-format dump restores fine serially but fails with
pg_restore -j 2: the child table's COPY runs before the parent's data is loaded, and the FK rejects it.

Serial restore: succeeds. Parallel restore (-j 2): failed 5 of 5 runs with

  pg_restore: error: COPY failed for table "child": ERROR:  insert or update on table "child" violates foreign key constraint "child_parent_id_fkey"
  DETAIL:  Key (parent_id)=(500000) is not present in table "parent".

The archive shows why: the child's TABLE DATA entry depends only on its own TABLE, not on the parent's TABLE DATA.

  pg_restore -l -v config_fk_order.dump
  3673; 0 55538785 TABLE DATA config_fk_order parent ...
  ;	depends on: 221
  3674; 0 55538791 TABLE DATA config_fk_order child ...
  ;	depends on: 222

Cause, as far as we can tell from the source

processExtensionTables() adds the child-data -> parent-data dependency (commit ebd092bc2a07, "Fix pg_dump handling
of extension config tables", 2015, CommitFest #110). But dumpTableData() passes only the own TABLE dependency to
ArchiveEntry(), and BuildArchiveDependencies() skips entries that already have these special dependencies (since
8a504a363925, 2012). So the data-to-data edge is used for pg_dump's own sort order but never reaches the archive,
and the parallel scheduler in pg_restore cannot see it. The same structure is in current master and REL_18_STABLE.

A possible fix is to append the selected referenced TABLE DATA dump IDs to the TABLE DATA entry's dependency list,
keeping the own TABLE ID first, since buildTocEntryArrays() maps TABLE -> TABLE DATA from dependencies[0].

Reproducer

config_fk_order.control:

  comment = 'pg_dump config-table FK ordering reproducer'
  default_version = '1.0'
  relocatable = false

config_fk_order--1.0.sql:

  CREATE SCHEMA config_fk_order;
  CREATE TABLE config_fk_order.parent (
      id integer PRIMARY KEY
  );
  CREATE TABLE config_fk_order.child (
      id integer PRIMARY KEY,
      parent_id integer NOT NULL REFERENCES config_fk_order.parent (id)
  );
  SELECT pg_catalog.pg_extension_config_dump('config_fk_order.parent', '');
  SELECT pg_catalog.pg_extension_config_dump('config_fk_order.child', '');

Commands (install the two files in the extension directory, or point extension_control_path at them):

  createdb config_fk_src
  psql -d config_fk_src -c "CREATE EXTENSION config_fk_order"
  psql -d config_fk_src -c "INSERT INTO config_fk_order.parent SELECT i FROM generate_series(1, 500000) AS g(i); INSERT INTO config_fk_order.child VALUES (1, 500000);"
  pg_dump -Fc -f config_fk_order.dump config_fk_src
  createdb config_fk_serial
  pg_restore --exit-on-error -d config_fk_serial config_fk_order.dump       # succeeds
  createdb config_fk_parallel
  pg_restore --exit-on-error -j 2 -d config_fk_parallel config_fk_order.dump # fails as above

We hit this with the sql_saga extension (temporal tables), whose catalog tables reference each other; we currently
document a split restore as a workaround.
