## Goal
The PL/pgSQL planner keeps null values inside a jsonb data column, as the native planner does

## Purpose
Under the PL/pgSQL planner temporal_merge writes [1, {"k": null}] as [1, {}] and {"n": null} as {}: jsonb_strip_nulls strips nested nulls, while only top-level payload keys were meant

## Principle
Strip only top-level payload keys (the column being NULL); never alter a jsonb column's value; identical results under both planners

## Relevant details
Situation: src/2k_temporal_merge_plan.sql calls jsonb_strip_nulls on whole data payloads (PATCH payload near line 1253, running payload merge near 1607/1637/1667, data_hash near 2406, provenance comparison near 2425/2467). jsonb_strip_nulls recurses into values, so a jsonb column holding nulls loses them. Measured 2026-11-22 on the 1.11 candidate (scratch database since dropped): a source jsonb [1, {"k": null}] is stored as [1, {}] and {"n": null} as {} under the PL/pgSQL planner, unchanged under the native planner. Test 162 deliberately avoids nested nulls (its scenario comment points here); the fix should add that case to test 162. Present since v1.0. Change: a shallow strip that removes only top-level keys whose value is JSON null, at every site. Why: a silent change of stored data, and the planners disagree. Cost: one expression or helper and the call sites; PL/pgSQL plan text changes for every era, so benchmark 101 under the PL/pgSQL planner before and after. Question: none.
