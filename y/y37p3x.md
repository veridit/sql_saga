## Goal
The PL/pgSQL planner keeps null values inside a jsonb data column, as the native planner does

## Purpose
Under the PL/pgSQL planner temporal_merge writes [1, {"k": null}] as [1, {}] and {"n": null} as {}: jsonb_strip_nulls strips nested nulls, while only top-level payload keys were meant

## Principle
Strip only top-level payload keys (the column being NULL); never alter a jsonb column's value; identical results under both planners

## Relevant details
Situation: src/2k_temporal_merge_plan.sql calls jsonb_strip_nulls on whole data payloads (PATCH payload at about line 1253, running payload merge at 1607/1637/1667, data_hash at 2406, provenance comparison at 2425/2467). jsonb_strip_nulls recurses into values, so a jsonb column holding nulls loses them. Seen 2026-11-22 on 1.11 candidate (scratch db arr_jhf): PL/pgSQL [1, {}], native [1, {"k": null}]; test 162 shows it. Present since v1.0. Change: a shallow strip, e.g. (SELECT coalesce(jsonb_object_agg(k, v), '{}') FROM jsonb_each(p) AS e(k, v) WHERE v <> 'null'::jsonb), as a small immutable sql_saga function used at every site. Why: silent data change, and the planners disagree. Cost: one helper and the call sites; plan caches change for every era (benchmark check). Question: none.
