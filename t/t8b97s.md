## Goal
The 1.15 lock step locks a 1,000 to 30,000 row batch in milliseconds for every key shape, measured against 1.14.

## Purpose
Found benchmarking 40nwvn: test 112 'SEED stat_for_unit (ES)' takes 95-101 s on 1.15 (7rzgv5's lock step) against 3.1 s on 1.14. The row-lock statement for the XOR natural key (establishment_id, stat_definition_id) IN (SELECT ... FROM source view) is planned as a nested loop over the index on stat_definition_id: 285,780,000 rows removed by join filter, 26.5 M buffers, 48 s. Earlier 'before' benchmarks were invalid: the v1.x build failed (update_step.sql names a 1.15 change) and silently measured the installed 1.15.

## Principle
Measure first; plan shape must not depend on a source view's estimates. Fix the statement, not the benchmark. Benchmarks compare against a real 1.14 install (git worktree at v1.14).

## Details
Repro: tmp/bench40/112_lock.sql and 112_variants*.sql (saga_112_jhf). Materializing the distinct keys first (subquery with OFFSET 0, or a MATERIALIZED CTE) gives a hash/merge join on the target's index: 0.1 ms on the same data. Row constructor = ANY(ARRAY(ROW(...))) is worse (34 s, seq scan).
