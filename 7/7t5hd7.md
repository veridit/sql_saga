## Goal
temporal_merge writes every data column type exactly and identically under both planners

## Purpose
Data columns of non-scalar type are written wrong: the PL/pgSQL planner fails on arrays, composites and jsonb strings; the native default planner stores a new entity's later jsonb slices as JSON strings

## Principle
One canonical JSON payload from both planners and one typed decoder in every executor path; results identical under both planners; no change for scalar columns

## Relevant details
Situation (re-measured 2026-11-22 on 1.10, scratch db arr_jhf; draft failing test sql/162_temporal_merge_typed_payload.sql with expected output = native results): the planners put different JSON in plan.data. PL/pgSQL emits canonical to_jsonb values (arrays as JSON arrays, composites as objects, jsonb as itself); native (native/src/reader.rs parse_typed_value) emits integers/booleans as JSON values, numeric as an f64 number (see nw3qmt), everything else as a JSON string of its text form. The executor (src/2l_temporal_merge_execute.sql and the copy in native/src/executor_cache.rs) decodes three ways: UPDATE SET and MERGE INSERT use (data->>'c')::type, founding-history INSERT uses jsonb_populate_record. Failures: (1) PL/pgSQL planner: any array or composite column fails (malformed array literal), and a jsonb holding a JSON string fails (invalid json). (2) Native planner: a jsonb column on a new entity's second slice is stored as a JSON string (jsonb_populate_record on the text form), observed: '{"v": 2}' stored as string. Both since v1.0. Change: one canonical payload (to_jsonb of each value) from both planners, one decoder (jsonb_populate_record, i.e. typed) in all three executor paths. Why: silent wrong values in the default planner; the PL/pgSQL planner is the reference. Cost: reader.rs emits canonical JSON (keeping text where it is exact), executor_cache.rs and 2l share the decoder; coalescing compares canonical values (1.1 vs 1.10 numeric must be equal: compare after decode or normalize). Question: none.
